## 1. Protocol / on-chain logic

### H1 — HIGH · §4a digest does not bind the proposals contract instance
`knot-proposals/src/state.rs:145`, `knot-encoding/src/lib.rs:227`

The signing preimage is
`DOMAIN || chain_id || committee_id || nonce || target || fn || args || deadline`.
It does **not** include the `knot-proposals` contract's own id.

You have already redeployed this contract three times (v0.3.0 → v0.3.1 → v0.3.2) on
`chain_id = 2`, against the same registry. An approval signature collected on the old
deployment is **byte-identical valid** on the new one for the same
`(committee_id, nonce, target, fn, args, deadline)`. Any member signature captured
from a superseded deployment — or from a second proposals contract someone else
deploys pointing at your registry — can be replayed.

`abi::verify_bls` in `approve()` only checks the signature against the digest; nothing
scopes it to *this* contract.

**Fix:** fold `abi::self_id()` into the preimage as a v2 domain (`...proposal.v2`),
keep v1 accepted only for a migration window, or don't — a clean break is cleaner
pre-mainnet. This is the single most important protocol change to make before the
code is public and before mainnet.

### H2 — HIGH · `change_account` digest binds neither chain nor registry instance
`knot-encoding/src/lib.rs:88`

`DOMAIN || account_id || nonce || pks || threshold`. No `chain_id`, no registry
contract id.

The same committee registered at the same `account_id` with the same `nonce` on two
registry deployments (testnet ↔ mainnet, or old ↔ new registry) shares a digest. A
quorum signature harvested on testnet — where keys are handled casually, per your own
README — replays against mainnet. Registry account `0` on testnet is already live with
alice + partner at nonce 0; the mainnet registry will also start at account 0, nonce 0.

**Fix:** same as H1 — add `chain_id` and `abi::self_id()` to
`DOMAIN_CHANGE_ACCOUNT_V1`'s preimage under a v2 tag. Treat any signature ever produced
against a testnet key as burned.

### M1 — MEDIUM · Proposal deadline is attacker-controlled and uncapped
`knot-proposals/src/state.rs:130-143`

`proposal_ttl` is only a *default* applied when `args.deadline == 0`. A caller passing
an explicit `deadline` bypasses it entirely — `u64::MAX` creates an immortal proposal
whose collected approvals never expire. Since `propose` is permissionless, anyone can
create these.

**Fix:** cap explicit deadlines at `block_height() + proposal_ttl` (or a separate
`max_ttl`), and reject anything beyond.

### M2 — MEDIUM · Permissionless `propose` + unbounded state + a wipe that can brick config
`knot-proposals/src/state.rs:117, 328`

`propose` has no caller gate, no deposit, no rate limit. `proposals` and `by_digest`
grow forever; nothing is ever pruned, even for expired or executed proposals.

`wipe_open_proposals()` iterates **every** proposal and is called by `init_registry`,
`init_chain_id`, and `set_proposal_ttl`. Once the map is large enough that the iteration
exceeds the gas limit, all three owner-only setters become permanently uncallable — the
contract's configuration is bricked and the only recovery is redeploy (which reopens H1).

**Fix:** (a) a `purge_expired(limit)` method callable by anyone, (b) make the wipe
paginated or replace it with an epoch counter folded into the digest so old proposals
are invalidated by construction rather than by iteration.

### M3 — MEDIUM · Stale-nonce proposals are permanently stranded
`knot-proposals/src/state.rs:270-273`

`finalize` requires `proposal.nonce == current_nonce`. When one proposal for a committee
finalizes, every *other* Open proposal at that nonce becomes permanently unfinalizable —
stuck `Open` forever with real approvals attached, occupying state, never expiring unless
a deadline was set.

Not exploitable, but it is a footgun that will confuse integrators and it compounds M2.
Document it prominently, or auto-tombstone siblings on finalize.

### L1 — LOW · Unchecked increment breaks the crate's own convention
`knot-proposals/src/state.rs:169` uses `self.next_id += 1`;
`knot-registry/src/state.rs:53` uses `checked_add(1).expect(...)`. Release WASM wraps
silently. Practically unreachable at u64 but make it consistent.

### L2 — LOW · Off-by-one between propose and approve/finalize deadline checks
`propose` rejects `deadline <= block_height()`; `approve`/`finalize` reject
`block_height() > deadline`. At exactly `height == deadline` the latter two still accept.
Pick one comparison.

### L3 — LOW · Diagnostic methods are permanent public attack surface
`knot-registry/src/state.rs:80-138` — `account_meta`, `member_key_bytes`,
`next_account_id`, `diagnose_quorum` were added to debug testnet RUES free-reads.
`diagnose_quorum` performs full `abi::verify_bls` work per call on a free-read path.
Bounded by `sigs.len() <= members.len() <= 16`, so not a serious DoS — but this is
debug scaffolding you are about to ship as permanent, immutable contract ABI. Decide
deliberately whether it stays.

### INFO — `verify_quorum` replay is the caller's problem
`knot-registry/src/state.rs:146`. Correctly and thoroughly documented in
`call_types.rs`. It is nonetheless the sharpest edge in the public API: any integrating
contract that calls `verify_quorum` with a nonce-free `msg` gets replayable
authorization. Promote this from a doc comment to a bolded warning in the registry
README and in `docs/security-model.md`.

### INFO — Rogue-key assumption is undocumented
`verify_quorum_aggregate` relies on `abi::verify_bls_multisig`. `sign_multisig(sk, pk, msg)`
taking the public key strongly suggests dusk uses message augmentation / key-prefixing,
which defeats the classic rogue-key attack on aggregate BLS. **Verify this against
dusk-core and state it explicitly in the security model**, because if it were plain
aggregation, a member who chose `pk_rogue = pk_target − Σ(other pks)` could forge an
aggregate for the entire committee alone. Members are registered as bare public keys
with no proof of possession, so the whole scheme rests on this property.

## 2. Key handling and the signing tool

### M4 — MEDIUM · Keystore file is briefly world-readable
`knot-tool/src/keystore.rs:213-218`

```rust
fs::write(path, &out)?;
fs::set_permissions(path, Permissions::from_mode(0o600))?;
```

`fs::write` creates the file under the process umask — typically `0o644`. Secret key
material is readable by every local user for the window between the two calls.

**Fix:** `OpenOptions::new().write(true).create(true).truncate(true).mode(0o600)`.
Also create `~/.knot-tool/` itself with `0o700` (`create_dir_all` uses `0o777 & !umask`).

### M5 — MEDIUM · Keystore write is not atomic — a crash destroys all keys
`fs::write` truncates in place. Interrupted mid-write (power loss, OOM, full disk) the
store is unrecoverable and every identity is gone. There is no backup path and no
warning in the docs.

**Fix:** write to `identities.dat.tmp`, `fsync`, then `rename`. Rename is atomic on the
same filesystem.

### M6 — MEDIUM · Decrypted secret material is never zeroized
`keystore.rs:126-168`. The code carefully zeroizes the 32-byte derived key and the
decoded `sk_bytes_vec` — but the `plaintext: Vec<u8>` holding **every secret key in the
store as hex JSON** is dropped without wiping, as is each `sk_hex: String` and, in
`save`, the freshly serialized `plaintext`.

**Fix:** wrap all three in `zeroize::Zeroizing`.

### M7 — MEDIUM · Key file format has no version or KDF parameters
Layout is `[salt:16][nonce:12][ciphertext]` with `PBKDF2_ROUNDS` hardcoded. You have
already been bitten by this once — the `load` error message tells users to *delete their
keystore* because the round count changed from 100k to 600k. The next parameter change
does the same thing again.

**Fix:** prepend a version byte + KDF id + parameters, and bind that header as AES-GCM
associated data. Consider Argon2id over PBKDF2 while you are changing the format.

### L4 — LOW · Derived key survives on the error path
`keystore.rs:126-135` and `:203-206` — `key_bytes.zeroize()` sits *after* a `?`. On wrong
password or encryption failure the derived key stays in memory. Use a drop guard.

### L5 — LOW · `parse_pk` format sniffing is fragile
`keystore.rs:101` — `t.chars().all(is_ascii_hexdigit)` routes to hex. A base58 key that
happens to contain only `[0-9a-fA-F]` is misrouted and fails with a confusing error.
Dispatch on length first, or try both and report both failures.

### L6 — LOW · `default_path()` panics without `$HOME`
`keystore.rs:68` — `.expect("HOME must be set")`. Use the `directories`/`dirs` crate or
return a `Result`.

### M8 — MEDIUM · The blob `threshold` field is unauthenticated but treated as a guard
`knot-tool/src/blob.rs:299, 502`

For `kind=proposals`, `threshold` is **not** part of the §4a preimage —
`gate_blob_for_signing` recomputes the digest from intent fields only. Yet
`aggregate_partials` and `build_pm_resolve_args` enforce
`partials.len() >= blob.threshold` and print "REFUSING".

A hostile blob simply sets `threshold: 1`. The check reads like a security control and
is not one. (The PM path is fine — `council_resolve_digest` does bind threshold.)

On-chain `finalize` re-checks against the registry, so no funds are at risk. But the CLI
message misleads the operator.

**Fix:** either fetch the real threshold from the registry before aggregating, or
re-label the message as an unauthenticated sanity check.

### M9 — MEDIUM · One poisoned partial silently invalidates the whole aggregate
`blob.rs:493` + `knot-collector/src/api.rs:152`

`aggregate_partials` never verifies individual partials — it deserializes and sums them.
Your own `VerifyQuorumAggregateArgs` doc states the property: *"a single wrong or missing
signer in `signer_keys` invalidates the whole aggregate."*

Combined with the collector accepting **unauthenticated last-write-wins overwrites** of
any partial by anyone who knows the proposal id (which is just the public digest), this
is a cheap remote griefing attack: overwrite one partial with 48 random bytes and every
subsequent aggregate fails on-chain, with no local diagnostic pointing at the culprit.

**Fix (tool side, the important one):** verify each partial locally with `verify_multisig`
before aggregating; drop and name the invalid ones. This fixes the griefing regardless of
what the collector does.

### L7 — LOW · `bls::aggregate` panics on an empty slice
`bls.rs:30` — `.expect("at least one signature to aggregate")`. Callers guard it today;
return a `Result` so a future caller can't panic the CLI.

### L8 — LOW · Blob files written non-atomically, no permission hardening
`blob.rs:404`. Blobs hold no secrets so this is minor, but the same atomic-write helper
used for M5 should cover it.

## 3. Collector (untrusted relay)

### M10 — MEDIUM · Unauthenticated partial overwrite (see M9)
`api.rs:152-192`, asserted as intended behavior by
`create_then_get_then_append_partial_then_list`. Last-write-wins by `signer_pk` with no
authentication. Anyone who knows the digest can clobber a real signature.

The trust model says a collector compromise "can at worst cause a DoS" — accurate, but
the README frames DoS as a compromise scenario when in fact **any anonymous internet user
can trigger it** on a reverse-proxied deployment. Fix in the tool (M9) and state the
property plainly.

### M11 — MEDIUM · No cap on proposal count or roster size
`MAX_PARTIALS = 32` and `MAX_BODY_BYTES = 64 KiB` are enforced, but nothing limits the
number of distinct proposals or party rows. At 64 KiB per POST an anonymous client fills
the SQLite volume. There is no retention policy, no TTL, no eviction.

**Fix:** row caps + a TTL sweep, and document that operators must set proxy-level rate
limits. Note the loopback guard does not help — the documented deployment is behind a
reverse proxy.

### M12 — MEDIUM · Party roster allows unauthenticated impersonation
`api.rs:201` — `POST /v1/party` takes `{name, pk, note}` with zero proof that the caller
controls `pk`. Anyone can register a real council member's public key under any name, or
their own key under a trusted member's name. The roster is a *rendezvous* surface people
will use to pick counterparties.

"It authorizes nothing" is true and insufficient — the risk is social, not cryptographic.

**Fix:** require a signature over `name || pk` (the tool already has the key), or put an
explicit impersonation warning in the API docs and the UI.

### L9 — LOW · `append_partial` skips id validation
`api.rs:157` lowercases the id but never calls `validate_proposal_id`, unlike
`get_proposal:141`. Arbitrary-length strings reach the query. Fails closed with 404, but
fix the inconsistency.

### L10 — LOW · Internal errors leaked to clients
`api.rs:129, 136, 148, 190, 197, 223` — `e.to_string()` on SQLite errors returns database
schema details and file paths in the HTTP 500 body. Log the detail, return a generic
message.

### L11 — LOW · Loopback guard is string matching, not address parsing
`lib.rs:56` — `bind.starts_with("127.0.0.1:")`. Rejects IPv6 loopback `[::1]:8899` and
bare `127.0.0.1`. It fails *closed*, so it is not a hole — but parse to `SocketAddr` and
test `ip().is_loopback()`.

### L12 — LOW · No graceful shutdown, no request tracing
`main.rs:38` — `axum::serve` without `.with_graceful_shutdown(...)`; SIGTERM can interrupt
a SQLite write. `tracing_subscriber` is initialized but no `TraceLayer` is installed, so
there is no request log for an internet-facing service.

## 4. Encoding crate

### L13 — LOW · `change_account` preimage deviates from the length-prefix discipline
`lib.rs:88` concatenates member keys with no count prefix. Because keys are fixed 96 bytes
and `threshold` is a fixed 4-byte suffix, the parse is unambiguous and there is **no
collision** — but the crate's headline property is "malleability-free length-prefixed
encoding", and this function quietly does not follow it. Add the count for uniformity when
you cut the v2 domain for H2.

### L14 — LOW · `recompute_and_verify` / `gate_blob_for_signing` return `Result<_, ()>`
Callers cannot distinguish "digest mismatch" from "field too large". `blob.rs:445` papers
over this with a hardcoded message that is wrong in the overflow case.

### INFO — PM-specific constant in a generic crate
`DOMAIN_COUNCIL_RESOLVE_V2 = "sme-platform.prediction-market.council-resolve.v2"` lives in
the general-purpose encoding crate. A public reader will ask why a multisig encoding
library knows about prediction markets. Either split it into a `pm` feature or explain
the coupling in the README.

### INFO — Domain tags are branded `sme-platform`
Every domain separator says `sme-platform.*` while the product is called Knot and the
repo is `aichbindas/knot`. You cannot change these without invalidating deployed
contracts and every signature ever produced. **Add a one-line note in the encoding README
explaining the historical name** — otherwise it reads as an accidental leak of an internal
codename, which is exactly what it is.

### INFO — Version drift
`knot-encoding/Cargo.toml` says `0.1.2`; root `README.md:32` says `0.1.1`. The README
also pins consumers to repo tag `v0.1.0`. Reconcile before publishing.

## 5. What is *right* — worth saying

The core anti-blind-signing design is sound and unusually well tested. Specifically:

- `human_summary` is structurally excluded from every digest, and there are explicit
  adversarial tests (`adversarial_lying_human_summary_ignored_for_digest`) proving a
  lying summary cannot induce a signature.
- Length-prefixed §4a encoding with a field-shifting collision test.
- Full 32-byte fingerprints with no truncation anywhere, plus a BIP39 golden vector.
- Registry dedupes signers before counting toward quorum, and early-rejects
  `sigs.len() > members.len()`.
- `finalize` re-verifies through the registry rather than trusting its own approval
  count, so a `change_account` between approve and finalize correctly invalidates
  stale approvals.
- CEI ordering in `finalize` with terminal status set before `call_raw`; reentrancy
  into `finalize` correctly panics on "not open".
- Collector genuinely cannot forge — no `dusk_core` dependency, enforced by module
  structure, and it discards caller-supplied partials at create time.
- `publish = false` on the contract crates prevents accidental crates.io publication.

The gaps above are mostly *scoping* gaps (H1, H2), *availability* gaps (M2, M5, M9–M11),
and hygiene — not breaks in the central signing argument.
